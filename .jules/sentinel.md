## 2025-01-20 - Fix DOM-based XSS in Link Interception
**Vulnerability:** A DOM-based Cross-Site Scripting (XSS) vulnerability existed in `premium.js` where link interception logic failed to securely block malicious URIs. Specifically, `href.startsWith('javascript')` could be bypassed using whitespace (e.g., ` javascript:alert(1)`), and `data:` URIs were not blocked at all. Furthermore, the check didn't call `e.preventDefault()`, allowing the browser to natively execute the payload.
**Learning:** Simple string prefix checks (like `startsWith`) are insufficient for validating URLs because browsers are lenient and will strip leading whitespace before executing protocol handlers. Additionally, security checks must explicitly block execution (via `e.preventDefault()`) rather than just exiting the custom script logic.
**Prevention:** Always use rigorous regular expressions (e.g., `/^\s*(javascript|data)\s*:/i`) to validate user-controlled or intercepted URLs against potentially executable schemes. Separate security intercept logic from normal control flow, ensuring that malicious attempts are actively stopped (`e.preventDefault()`) before returning.

## 2025-01-20 - Fix DOM-based XSS via Protocol Scheme Bypass
**Vulnerability:** The link interception in `premium.js` was modified previously to use a regex to detect protocol handlers `(/^\s*(javascript|data)\s*:/i.test(href))`. However, browsers silently strip various non-printable and control characters `(\x00-\x1F)` embedded within the protocol component. Thus, payloads like `\x01javascript:alert(1)` successfully bypassed the check and executed, as they didn't match the regex pattern expecting the URL string to start with "javascript" (even with leading whitespaces accounted for).
**Learning:** Checking for prefixes or utilizing `^\s*` is still an incomplete mitigation strategy for URLs. Given that the browser sanitizes control characters before resolving the scheme, security logic MUST perform the exact same sanitization (e.g., stripping `\s` and `\x00-\x1F` characters) *before* validating the protocol, otherwise bypasses using invisible control characters will succeed.
**Prevention:** Before validating an untrusted or user-supplied URI against dangerous protocols, explicitly sanitize the input by replacing all whitespace and control characters `(e.g., href.replace(/[\s\x00-\x1F]/g, ''))`. This ensures the validation logic accurately predicts how the browser will interpret the resulting URI.
